# Rizo Lang Specification

Version 0.6 · Milestones 1–9 (Milestone 10 in progress: `with` and the `site` line are on `main`, not yet released)

Rizo Lang is a secure, simple, full-stack web language. Source files end in `.rz`. The compiler, `rizolang`, turns Rizo Lang into existing technology: a PostgreSQL schema, TypeScript types, a Node.js server and web pages.

This document is the complete language reference. It is written for people and for AI models alike. If something is not described here, it is not part of the language.

> **Status:** `model`, `auth`, `api` and `page` blocks and the `privacy` and `site` lines are available. Other blocks are not available, and using them is a compile error (RZ0211).

---

## 1. Design rules

1. **Dangerous mistakes are impossible, not just unlikely.** There is no raw SQL and no way to build a query from text.
2. **Strict and clear.** Every value has a static type. Every error says what went wrong, where and how to fix it.
3. **Small.** The whole language fits in this document.
4. **Secure by default.**
   - Passwords are hashed automatically and can never be returned in an API response or logged.
   - Inputs are validated automatically.
   - Login and ownership checks are part of the syntax.

---

## 2. Files and basic syntax

- A source file is UTF-8 text with the extension `.rz`.
- A file contains `model` blocks, at most one `auth` line, at most one `privacy` line, at most one `site` line, `api` blocks and `page` blocks, in any order.
- Comments start with `//` and run to the end of the line. A comment after a path needs a space before it.
- Whitespace separates tokens. Indentation has no meaning, but two spaces are conventional.
- **One item per line.** Each field, and each statement in an `api` block, goes on its own line. Commas appear only in lists: query arguments, roles (`roles`, `requires role`), `privacy for` regions and `with` links.
- Names contain only ASCII letters and digits and start with a letter. Underscores and hyphens are not allowed in names.
- Numbers are whole numbers, optionally negative: `100`, `0`, `-5`. Decimals are not allowed.
- Quoted text (`"Latest posts"`) is allowed only in `page` blocks and the `site` line. It stays on one line, has at most 200 characters, and can only escape `\"` and `\\`.
- Lines and columns in error messages start at 1. A tab counts as one column.

## 3. Models

A model describes one kind of record stored in the database.

```rizo
model User {
  email: Email unique private
  password: Password
  name: Text max 100
}

model Post {
  author: User
  title: Text max 200
  published: Bool
}
```

- A model starts with the lowercase keyword `model`, then a PascalCase name, then `{`. It ends with `}`.
- A model has at least one field. Model names are unique in a file, and field names are unique in a model.
- A field is written `name: Type` followed by zero or more modifiers, all on one line.
- Every model automatically gets an `id: ID` field (a UUID generated by the database). **Do not declare `id`.**

### 3.1 Field types

| Type       | Meaning                                       | PostgreSQL    | TypeScript     | Modifiers allowed                    |
|------------|-----------------------------------------------|---------------|----------------|--------------------------------------|
| `Text`     | Text. At most 10,000 characters by default.   | `TEXT`        | `string`       | unique, optional, private, encrypted, min, max |
| `Number`   | Whole number, −2147483648 to 2147483647.      | `INTEGER`     | `number`       | unique, optional, private, encrypted, min, max |
| `Bool`     | `true` or `false`.                            | `BOOLEAN`     | `boolean`      | optional, private                    |
| `Email`    | Email address, 3–254 chars, stored lowercase. | `TEXT`        | `string`       | unique, optional, private, encrypted, min, max |
| `Password` | Stored only as a salted hash.                 | `TEXT` (`<name>_hash`) | `PasswordHash` | optional, min, max          |
| `Date`     | Date and time, in UTC.                        | `TIMESTAMPTZ` | `Date`         | unique, optional, private, encrypted |
| `ID`       | A UUID.                                       | `UUID`        | `string`       | unique, optional, private            |
| *Model*    | A link to a record of that model.             | `UUID` (`<name>_id`) + foreign key | `string` | unique, optional, private |

- `Number` is for whole numbers. Store money as cents.
- `Email` values are trimmed and lowercased. They must look like `name@domain.tld`.
- `Password`:
  - The plain-text password is never stored. `password` is stored as `password_hash`.
  - `min` and `max` limit the plain-text length. The defaults are 8 and 128, and you can only tighten them.
  - A field named `password`, `passwd`, `pwd`, `passcode` or `passphrase`, or ending in `Password`, `Passwd`, `Passcode` or `Passphrase`, must have the type `Password`.
- **Links:** a field whose type is another model's name, such as `author: User`.
  - It stores that record's id in the column `<name>_id`, with a foreign key and an index.
  - Models may link in any order, and a model may link to itself.
  - A required link cannot point to a record that doesn't exist. A record that others link to cannot be deleted.
  - When the linked record is deleted, an optional link becomes `null`.

### 3.2 Modifiers

Modifiers come after the type, on the same line, in any order, each at most once.

| Modifier   | Meaning                                                                                        |
|------------|------------------------------------------------------------------------------------------------|
| `unique`   | No two records may have the same value.                                                        |
| `optional` | The value may be missing (`null`). Without it, the field is required.                          |
| `private`  | Stored and accepted as input, but **never returned** by any endpoint, and not allowed in filters or ordering. |
| `encrypted` | Text, Email, Number, Date: stored encrypted (AES-256-GCM), so the database and its backups never see the value. See below. |
| `min N`    | Text, Email, Password: minimum length in characters. Number: minimum value.                    |
| `max N`    | Text, Email, Password: maximum length in characters. Number: maximum value.                    |

| Type       | Default min | Default max | Allowed range for `min`/`max` |
|------------|-------------|-------------|-------------------------------|
| `Text`     | none        | 10000       | 0 to 1000000 (`max` ≥ 1)       |
| `Email`    | 3           | 254         | 3 to 254                      |
| `Password` | 8           | 128         | 8 to 128                      |
| `Number`   | none        | none        | −2147483648 to 2147483647     |

- `min` must be ≤ `max` after defaults are applied.
- `unique` is not allowed on `Bool` or `Password`.
- `min` and `max` are not allowed on `Bool`, `Date`, `ID` or links.
- `private` is not allowed on `Password`, which is always hidden.

**Encrypted fields.** `phone: Text optional encrypted` is encrypted by the server before it is written, and decrypted when it is read.
- Endpoints send and receive the plain value, and limits (`min`, `max`, email format) are still checked. Combine with `private` to also keep it out of responses.
- Each value gets a random IV and is tied to its table and column, so a value copied into another column can't be decrypted.
- The database can't compare encrypted values, so an encrypted field can't be `unique`, the login field, a `list` filter or an `order` (RZ0340).
- Keys come from `RIZO_ENCRYPTION_KEYS` (§6). Without them, an app with encrypted fields refuses to start.
- **Rotating keys:** put a new key first in `RIZO_ENCRYPTION_KEYS`, keep the old ones after it, and restart. New values use the new key. Then run `node reencrypt.ts` to move stored values to it, and remove the old key once it reports nothing failed. If a key is lost, the values encrypted with it are lost too.
- Making an existing field encrypted (or no longer encrypted) replaces its column, which deletes its values (`--allow-data-loss`). To keep them, add a new encrypted field and copy the values over.

### 3.3 Naming

| Thing      | Style      | Example             | In PostgreSQL               |
|------------|------------|---------------------|-----------------------------|
| Model name | PascalCase | `BlogPost`          | table `blog_posts`          |
| Field name | camelCase  | `firstName`         | column `first_name`         |
| Link field | camelCase  | `author: User`      | column `author_id`          |

- **Table names** are the snake_case plural of the model name:
  - `+s` by default,
  - `+es` after `s`, `x`, `z`, `ch` or `sh`,
  - consonant + `y` becomes `ies`.
- **Reserved names:**
  - Model names: the seven type names, plus `PasswordHash`, `String`, `Boolean`, `Object`, `Array`, `Promise`, `Record`, `Error`, `Map`, `Set`, `Symbol`, `BigInt`, `Function`, `JSON`, `Math`, `Partial` and `Readonly`.
  - Field name: `id`.
- Two names must never produce the same table, column or TypeScript type. Table and column names must be at most 63 characters.

## 4. Login: the `auth` line

```rizo
auth User by email
```

This line turns on accounts and sessions. It is written `auth <Model> by <field>`, optionally followed by `roles <name>, <name>, ...`.

Rules (error RZ0317):
- The field must be declared as `Email unique`, and it must not be optional.
- The model must have exactly one required `Password` field.
- A link from the model to itself must be optional.
- There can be at most one `auth` line per file.
- Roles, if declared, are camelCase names, at most 20 of them, and must include `admin`. The model must not have its own field named `role`.

It adds these endpoints. Paths under `/auth` are reserved.

| Endpoint            | Body                              | Result                                        |
|---------------------|-----------------------------------|-----------------------------------------------|
| `POST /auth/signup` | The model's fields, like `User.input` | 202 `{ "message": ... }`, always the same (see below). Emails a link to confirm the address. Doesn't log in |
| `POST /auth/verify-email` | `{ "token": ... }` (from the emailed link) | 204: the email is confirmed. 400 if the link is invalid, used or expired |
| `POST /auth/verify-email/resend` | `{ "email": ... }` | 202, always the same. Emails a new link if the account exists and isn't confirmed |
| `POST /auth/password-reset` | `{ "email": ... }` | 202, always the same. Emails a reset link if the account exists |
| `POST /auth/password-reset/confirm` | `{ "token": ..., "newPassword": ... }` | 204: the password is changed, every session is logged out and the email counts as confirmed. 400 if the link is invalid, used or expired |
| `POST /auth/login`  | `{ "email": ..., "password": ... }` | 200 with `User.public`, or 401. 403 `email_not_verified` (only after a correct password) until the email is confirmed |
| `POST /auth/logout` | none                              | 204; the session is deleted                   |
| `GET /auth/me`      | none                              | 200 with `User.public`, or 401                |
| `PATCH /auth/me`    | Any profile fields                | 200 with `User.public`. Every field is optional. The login email, the password, the role and links to the auth model can't be changed here |
| `POST /auth/password` | `{ "currentPassword": ..., "newPassword": ... }` | 204. Every other session of the account is logged out |
| `POST /auth/email`  | `{ "newEmail": ..., "password": ... }` | Login required (cookie). 202, always the same: emails a link to the new address if no account uses it. Nothing changes until the link is opened |
| `POST /auth/email/confirm` | `{ "token": ... }` (from the emailed link) | 204: the login email is changed, and the old address is told. 400 if the link is invalid, used or expired; 409 if another account took the address meanwhile |
| `POST /auth/logout-all` | none                          | 204. Every session of the account is deleted, including this one |
| `GET /auth/sessions` | none                             | Login required. 200 `{ "items": [{ "id", "device", "createdAt", "lastSeenAt", "current" }] }`: the devices you are logged in on |
| `GET /auth/tokens`  | none                              | Login required (cookie). 200 `{ "items": [...], "endpoints": [...] }`: your API tokens (never the token itself), and the endpoints a token may be made for |
| `POST /auth/tokens` | `{ "name": ..., "endpoints": ["POST /api/posts", ...], "days": 1–90 }` | Login required (cookie). 201 with the token in `token`, shown only this once. `days` defaults to 90. 409 over 20 tokens |
| `DELETE /auth/tokens/:id` | none                        | Login required (cookie). 204: the token stops working. 404 if it isn't yours |
| `DELETE /auth/sessions/:id` | none                      | Login required. 204: that device is logged out (if it is this one, the cookie is cleared too). 404 if it isn't one of yours |
| `DELETE /auth/me`   | `{ "password": ... }`             | 204: the account is deleted (see "Your data" below). 409 only if records need an owner and no "Deleted user" account can be made |
| `GET /auth/privacy` | none                              | Public, only with `privacy for`: the privacy notice (§4.2) |
| `GET /auth/me/export` | none                            | Login required (cookie). 200 with everything stored about you, as a `my-data.json` download. At most 5 times an hour |
| `GET /auth/audit`   | `?account=<id>&limit=<1–500>` (optional) | Admins only (needs `roles admin`): the newest security audit entries, `{ "items": [...] }` |
| `POST /auth/passkeys/register-options` | none | Login required. 200 with WebAuthn creation options for this account |
| `POST /auth/passkeys` | `{ "name": ..., "credential": ... }` | Login required. 201 `{ "id", "name" }`. 409 if the passkey is already added or the account has 20 |
| `GET /auth/passkeys` | none | Login required. 200 `{ "items": [...] }`, this account's passkeys |
| `DELETE /auth/passkeys/:id` | none | Login required. 204, or 404 if it isn't one of your passkeys |
| `POST /auth/passkeys/login-options` | none | 200 with WebAuthn request options |
| `POST /auth/passkeys/login` | `{ "credential": ... }` | 200 with `User.public`, or 401; 403 `email_not_verified` until the email is confirmed. Counts toward the login limits |

**How login works**
- Passwords are hashed with scrypt (N=2^15, r=8, p=3) and a random salt.
- A wrong password and an unknown email give the same 401 response, in about the same time.
- After 5 failed logins for an account, or 20 from one address, within 15 minutes, login answers 429. Signups are limited to 10 per hour per address.
- Every `/auth` endpoint also has the default limit of 120 requests a minute per address. Opening emailed links (`/auth/verify-email`, `/auth/email/confirm`, `/auth/password-reset/confirm`) is limited to 30 an hour per address, and passkey login options to 30 a minute.

**Email.** Accounts must confirm their email address before they can log in.
- **Signup doesn't reveal who has an account.** It answers the same 202 whether or not the email is taken. A new email gets a confirmation link. If the email already has an account, nothing is created or changed, and the owner gets an email saying someone tried to sign up, with links to log in or reset the password. Other unique fields still answer 409.
- **Links** are `RIZO_PUBLIC_URL/verify-email#token=…` (works for 24 hours), `RIZO_PUBLIC_URL/reset-password#token=…` (1 hour) and `RIZO_PUBLIC_URL/confirm-email#token=…` (a new login email, 1 hour). Each works once, and sending a new one cancels the old one. Changing the login email or the password, or resetting the password, cancels every pending link of the account. Only SHA-256 hashes of tokens are stored. The token is after `#`, so it never reaches a server log, and link scanners in mail systems can't use it up: the page sends it with a POST. Apps without pages must handle these three paths in their own frontend.
- **Limits:** at most 3 emails an hour go to one account, and requests that send email are limited to 10 an hour per address.
- **Emails** are plain text, made of fixed sentences plus the link. Nothing from a request is put in them. They are sent through [Resend](https://resend.com) in the background, so the response never waits for them or depends on them, and failures are logged without the address.
- Accounts that existed before email confirmation was added count as confirmed.

**Your data.** Every app with an `auth` line lets people take and delete their data.
- **Export:** `GET /auth/me/export` returns `account` (every stored field except the password hash, private and encrypted ones included, since it is the person's own data), `records` (each model's records that link to the account, up to 10,000 per model; `truncated` lists any model with more), `devices`, `passkeys`, `apiTokens` and `securityLog` (their newest 500 audit entries). The role, if the app has roles, is part of `account`: it is the person's own data. It is recorded in the audit log as `data_exported`.
- **Deletion:** `DELETE /auth/me` deletes the account with its sessions, devices, passkeys and API tokens. Optional links to it become empty. Records that must link to an account, such as posts, are given to one shared **"Deleted user"** account in the same statement, so they stay but nothing points back to the person.
- The "Deleted user" account is created the first time it is needed. It holds only placeholders ("Deleted user", an address under the reserved `.invalid` domain) and has no password, so nobody can log in as it. If the auth model has a required link to another model, no placeholder can be made, and deletion answers 409 while such records exist.

**API tokens.** Scripts and AI agents can call your endpoints with an API token instead of a session cookie: `Authorization: Bearer rzt_...`.
- A token acts as the account that made it, but **only on the endpoints chosen** when it was made (any endpoint that needs a login). Other endpoints that need a login answer 403 `token_not_allowed`; public endpoints ignore the token.
- It expires after at most 90 days, can be revoked at any time, and is deleted with the account. A password reset revokes all of the account's tokens.
- Tokens never work on `/auth/*` endpoints, so a token can't make tokens, see sessions, change the password or delete the account. Those need a session cookie.
- When an `Authorization` header is sent, it is used instead of the cookie. An unknown, malformed or expired token answers 401 `invalid_token`.
- Only SHA-256 hashes are stored. Creating, using and revoking tokens are recorded in the audit log (each use with its endpoint).

**Passkeys.** Every app with an `auth` line also supports passkeys (fingerprint, face or device PIN), alongside passwords. A logged-in user adds one on the built-in `/account` page (or through the endpoints above), then logs in with it on `/login`. Nothing in the `.rz` file changes.
- The server checks each step as WebAuthn requires: a random challenge that is used once and expires after 5 minutes, the site's origin and id, that the user was verified, the signature, and that the signature counter went up (a counter that goes backwards means the key was copied, and login is refused).
- The site is taken from the request's `Origin` header, so requests without one get 400. Serve the app on its real domain (passkeys need HTTPS, or `localhost`).
- Only ES256 and RS256 keys are accepted. Attestation is not checked, so any authenticator can be added.
- The server stores only the public key. Passkeys are deleted with their account.

### 4.1 Roles

```rizo
auth User by email roles admin, editor
```

Each account has at most one role, or none.
- **Storage:** the role is kept in a hidden `role` column that only accepts the declared names.
- **Never from or to clients:** the role is never accepted in a request body and never appears in a public type or in any response, except the person's own data export.
- **Checked on every request:** a role change applies to existing sessions immediately.

**Assigning roles.** Admins use a built-in endpoint:

| Endpoint | Body | Result |
|----------|------|--------|
| `PUT /auth/users/:id/role` | `{ "role": "editor" }` or `{ "role": null }` | 200 `{ "id", "role" }`. Admins only: 401 if not logged in, 403 if not an admin or if it's your own account |

**The first admin.** Sign up normally, then start the server with `RIZO_ADMIN_EMAILS=you@example.com`. At startup, accounts that **already exist** with a listed email become admins. Accounts created later are never promoted this way, so nobody can claim admin by signing up with a listed email.

**Sensitive changes:**
- Changing the password and deleting the account need the current password.
- A wrong password gets 403. After 5 wrong passwords in 15 minutes, these changes answer 429 (a lockout of its own, separate from login's).
- New passwords follow the Password field's `min` and `max`.
- Changing the login email needs the password and a link sent to the new address (`POST /auth/email`, above).

**Security audit log.** Every app with a server records security events in the `_rizo_audit` table:
- **Events:** sign-ups; email confirmations and changes; logins, failed logins (with the account when it exists) and blocked logins; logouts and "log out everywhere"; devices logged out; password changes, wrong password checks, reset requests and resets; passkeys added and removed; API tokens created, used and revoked; data exports; account deletions; role changes; admins granted at startup; every record deleted through an endpoint; and records deleted by `keep`.
- **What each entry holds:** the time, the action, who did it, who or what was affected, the IP address, and a short fixed detail. Never a password, a token or a request body.
- **Retention:** entries are kept for `RIZO_AUDIT_RETENTION_DAYS` (365 by default), then deleted automatically.
- **Availability:** if an entry can't be written, the action still succeeds and the failure is logged.

**How sessions work**
- The session is a random 256-bit token in the `rizo_session` cookie: `HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=2592000` (30 days).
- The database stores only a SHA-256 hash of the token, in the table `_rizo_sessions`.
- A session ends after **7 days without use**, and **30 days after login** however much it is used. Using it moves the 7-day deadline forward (at most once a minute).
- Each session has a public id and a device label such as "Chrome on macOS", made only from fixed browser and system names. The raw User-Agent and the IP address are not stored.

### 4.2 Privacy: `privacy for` and `keep`

```rizo
privacy for EU, UK, IN, US-CA, BR

auth User by email

model User {
  email: Email unique private
  password: Password
}

model Message {
  sender: User
  body: Text
  keep 2 years
}
```

**`privacy for`** names the regions the app serves: `EU` (GDPR), `UK` (UK GDPR), `IN` (India's DPDP Act), `US-CA` (California's CCPA) and `BR` (Brazil's LGPD). At most one line, with each region once (RZ0341). It needs an `auth` line, because privacy rights belong to accounts. Every app with accounts already lets people download and delete their data (§4, "Your data"). These rules help an app meet the technical parts of these laws; they are not legal advice.

**The privacy notice.** With a `privacy for` line, the app publishes what it does with people's data, written for them, with no text to write:
- `GET /auth/privacy` (public JSON) and, in apps with pages, a built-in `/privacy` page linked from every page's menu.
- **What we store:** every model and field, and whether each is shown publicly, private, encrypted or stored only as a hash, and how long records are kept (`keep`, or until deleted).
- **Cookies:** the one login cookie, and why there is no cookie banner (no tracking).
- **Who else handles the data:** Resend for account emails, and a statement that personal information isn't sold, shared or used for advertising.
- **Security**, and how long security logs (with IP addresses) are kept (`RIZO_AUDIT_RETENTION_DAYS`).
- **Rights:** download (`/account`), delete (`/account`), and correction or questions through the contact; for each region, its law and where to complain.
- **Contact:** `RIZO_PRIVACY_CONTACT` (§6), which is required: an app with `privacy for` refuses to start without it.

**`keep N days|months|years`**, on its own line in a model, deletes records that long after they were created (`day`, `month` and `year` work too).
- From 1 day to 100 years. At most one per model. Not on the auth model: people delete their own accounts (RZ0342).
- It adds a hidden `_created_at` column (with an index). Records that already exist when `keep` is added count from the time of that migration.
- Every 10 minutes the server deletes expired records, 1,000 at a time and at most 20,000 per model, and writes one `records_expired` audit entry per model with the number deleted.
- A record that another record must link to (a required link) is kept until that record is gone.
- It needs a server, so the file must have an `auth` line, `api` or `page` blocks (RZ0342).

## 5. Endpoints and pages: `api` and `page` blocks

```rizo
api GET /posts/:id -> Post.public {
  public
  return db.Post.find(id)
}
```

An endpoint has a header, an access rule, an optional owner rule and one return line:

```
api <METHOD> <path> [-> <return type>] {
  public | requires login
  [requires role <role>, <role>]
  [requires owner <link field> [or role <role>, <role>]]
  [limit <number> per second|minute|hour|day]
  return db.<Model>.<action>(<arguments>)
}
```

### 5.1 Header

- **Method:** `GET`, `POST`, `PUT`, `PATCH` or `DELETE`, in uppercase.
- **Path:** starts with `/`.
  - Static segments use lowercase letters, digits and single hyphens.
  - Parameters are written `:camelCase`, for example `/posts/:id`.
  - No trailing slash, no empty segment, and no parameter may appear twice.
  - `me` and `body` cannot be parameter names.
- **Return type:**
  - `-> Model.public` for one record.
  - `-> list Model.public` for many records.
  - Nothing at all for `delete`.
  - Endpoints can only return the `.public` view.

### 5.2 Access

Every endpoint must contain **exactly one** of these lines (RZ0318):

- `public`: anyone may call the endpoint.
- `requires login`: the caller must have a valid session, otherwise the response is 401.

There is no default, so an endpoint can never be left open by accident. `requires login` needs an `auth` line.

`requires owner <field>` adds an ownership check (RZ0329):
- It needs `requires login` (RZ0318).
- `<field>` must be a link to the auth model, for example `author`.
- It works with `find`, `update` and `delete`.
- The check is part of the SQL `WHERE` clause. A record owned by someone else behaves exactly like a missing one (404), so callers can't tell that it exists.
- It is **required** for `update` and `delete` on a model that links to the auth model (RZ0331), unless the endpoint has `requires role`. That way one user can never change another user's records.
- `requires owner author or role admin` also lets the listed roles act on records they don't own. This check is part of the `WHERE` clause too.

`requires role admin, editor` only lets users with one of the listed roles call the endpoint; anyone else gets 403.
- It needs `requires login` (RZ0318), and the roles must be declared on the `auth` line (RZ0332).
- With `update` or `delete`, it lets those roles change any record.
- A public endpoint can't update or delete such a model either: `requires owner` needs `requires login`.

### Rate limits

Every endpoint is rate-limited. The default is **120 requests per minute**, counted per account for logged-in callers and per IP address otherwise. Built-in `/auth` endpoints and pages also get 120 per minute per address. Only the page runtime's files (`/_rizo/…`) and the health check have no limit. You can set your own limit:

```rizo
api POST /api/drafts -> Post.public {
  requires login
  limit 10 per minute
  return db.Post.create(body, author = me)
}
```

- The number is 1 to 100,000, and the unit is `second`, `minute`, `hour` or `day`. One `limit` line per endpoint (RZ0222, RZ0339). There's no way to turn limits off.
- Over the limit, the response is 429 with a `Retry-After` header. On `api` endpoints, requests already refused as cross-site (403), with invalid query parameters (400) or without a needed login (401) don't count. On `/auth` endpoints and pages, every request to a known path counts.
- Limits use a sliding window: requests from the previous window still count as they fade out, so there's no burst allowed at window edges.
- Counters live in PostgreSQL (`_rizo_rate_limits`), so the limits hold when the app runs on several servers.
- The table stores only hashes of IP addresses and account ids, never the values themselves, and old counters are deleted automatically.

### 5.3 Queries

The return line is `return db.<Model>.<action>(...)`. There are five actions. Each one has exactly one allowed method (RZ0328), so `GET` never changes data.

| Action   | Method        | Arguments                                         | Result                                    |
|----------|---------------|---------------------------------------------------|-------------------------------------------|
| `find`   | GET           | `(id)`: a path parameter                          | 200 with the record, or 404               |
| `list`   | GET           | filters, `order`, `limit` (all optional)          | 200 with `{ "items": [...], "next": ... }` (§5.4) |
| `create` | POST          | `(body)` then optional `field = value`            | 201 with the new record                   |
| `update` | PUT or PATCH  | `(id, body)`                                      | 200 with the updated record, or 404       |
| `delete` | DELETE        | `(id)`                                            | 204, or 404                               |

**`list` arguments**, separated by commas:
- `field OP value`: filters, combined with AND.
  - `=` and `!=` work on every field type.
  - `<`, `<=`, `>` and `>=` work on Number and Date fields.
  - `contains` works on Text and Email fields: a case-insensitive "includes" (`%` and `_` are plain characters). Its value comes from the request: `?q` or a path parameter (read as plain text, not a full email address).
  - A value is `me`, a path parameter, a number, `true`, `false`, or a **query parameter** such as `?q`.
- **Query parameters** (`?name`) let clients filter: `db.Post.list(title contains ?q, views >= ?minViews)` reads `/api/posts?q=rizo&minViews=10`.
  - Each one is optional: when it is left out or empty (`?q=`), its filter is skipped.
  - Its value must fit the field's type (text up to 200 characters, or the field's own maximum when compared with `=`), or the request answers 400 before any query runs. Unknown parameters also answer 400.
  - A name can't be `limit` or `after`, can't also be a path parameter, and keeps one type wherever it is used.
  - When asking for the next page, send the same filters along with `after`.
  - Query parameters only filter lists, and `create` sets fields only with `=` (RZ0325).
- `order field` or `order field desc`: sorts. The default order is by `id`. You can't order by an `optional` field, because pages need a sort value in every record.
- `limit N`: the largest page size, from 1 to 100. The default is 50.

Hidden fields (Password or `private`) cannot be used in filters or ordering.

**Linked records: `with`.** A `find` or `list` endpoint can return the records its links point to, after the return type: `api GET /api/posts -> list Post.public with author, editor`.
- Each listed link comes back as the linked record's public fields, such as `"author": { "id": ..., "name": "Ann" }`, or `null` for an empty optional link. Private and Password fields of the linked record are never included, and its encrypted fields are decrypted.
- It is still one database query: each linked record is read by its primary key.
- Pages show the linked record's first public Text or Email field ("Ann") instead of its id.
- Only public link fields of the returned model can be listed, each once, and only on `find` and `list` (RZ0343).

**Indexes are automatic.** For every `list`, the compiler creates an index on its `=` filter fields, then its order field (or, without one, its `<`/`>` fields), then `id`. Each page (including "Load more") is then read in order from the index instead of scanning the table; `<`/`>` filters on another field than the order narrow the rows as they are read. Migrations add and remove these indexes as your endpoints change. `contains` and `!=` can't use such an index, so on a large table combine them with an `=` filter, such as `author = me`. Text and Email fields that may be longer than 600 characters are not indexed (a longer value could overflow an index row), so give fields you filter or sort by a `max` of 600 or less.

**Values** on the right of `=`:
- `me`: the logged-in user. It only works with a link to the auth model, and is not allowed in public endpoints.
- A path parameter's name, such as `userId`. Its type comes from the field it's compared with.
- A whole number, for `Number` fields.
- `true` or `false`, for `Bool` fields.

**`body`** is the JSON request body. It is validated before the query runs:
- Unknown keys are rejected.
- Required fields must be present.
- `null` is only allowed for optional fields.
- Every limit from the model is checked.
- In `update`, every field is optional, and only the fields that are sent are changed.

**Ownership is never taken from the client** (RZ0326):
- A link to the auth model is never part of `body`.
- In `create`, it must be assigned `= me`: `db.Post.create(body, author = me)`.
- `update` can never change it.

The auth model itself cannot be created, updated or deleted through `api` blocks (RZ0327). Accounts are created through `/auth/signup`.

Every path parameter must be used in the query (RZ0323).

### 5.4 Pagination

A `list` endpoint returns one page at a time:

```
GET /posts?limit=10                →  { "items": [ ...10 posts... ], "next": "WyJIZWxsbyIs..." }
GET /posts?limit=10&after=WyJI...  →  { "items": [ ...the next posts... ], "next": null }
```

- `limit` is optional. It must be a whole number from 1 to the endpoint's `limit`, which is also the default.
- `after` is the `next` value from the previous page. `next` is `null` on the last page.
- Pages continue exactly after the last record of the previous page, ordered by the sort field and then by `id`. Records added between requests can't cause records to be skipped or repeated.
- Cursors are opaque. Clients must not build or change them. An invalid cursor is rejected with 400.
- Endpoints accept no other query parameters than `limit`, `after` and a list's own `?name` filters. Any unknown or repeated parameter gets 400, on every endpoint.

### 5.5 A complete example

```rizo
auth User by email

model User {
  email: Email unique private
  password: Password min 12
  name: Text max 100
}

model Post {
  author: User
  title: Text min 1 max 200
  published: Bool
}

api GET /posts -> list Post.public {
  public
  return db.Post.list(published = true, order title, limit 20)
}

api POST /posts -> Post.public {
  requires login
  return db.Post.create(body, author = me)
}

api PATCH /posts/:id -> Post.public {
  requires login
  requires owner author
  return db.Post.update(id, body)
}

api DELETE /posts/:id {
  requires login
  requires owner author
  return db.Post.delete(id)
}
```

### 5.6 Web pages: `page` blocks

A page shows data from the file's own endpoints. You never write HTML or browser code: the compiler generates the page.

```rizo
page / {
  public
  title "Rizo Blog"
  text "Stories from our writers."
  show GET /api/posts
}

page /posts/:id {
  public
  show GET /api/posts/:id
  link "Back to all posts" /
}
```

| Line | Meaning |
|------|---------|
| `public` or `requires login` | Who may see the page. Exactly one is required (RZ0333). `requires role admin` can be added after `requires login` |
| `title "..."` | The page heading and browser title. The default comes from the path (`/blog-posts` → "Blog posts", `/` → "Home") |
| `text "..."` | A paragraph |
| `link "..." /path` | A link to another page in the file, or to a built-in page (`/login`, `/signup`, `/account` and the others) when there is an auth line; `/privacy` also needs a `privacy for` line |
| `show GET /api/...` | The data to show, from a GET endpoint in the file. At most one per page |
| `form POST /api/...` | A form that creates a record (POST), or changes one (PUT or PATCH) |
| `button "..." DELETE /api/...` | A button that deletes a record, after asking "are you sure?" |
| `then go /path` | The page to open after the form or button succeeds. Required with a form or button |

```rizo
page /posts/:id {
  public
  show GET /api/posts/:id
}

page /posts/new {
  requires login
  title "Write a post"
  form POST /api/posts
  then go /posts/:id
}

page /posts/:id/edit {
  requires login
  form PATCH /api/posts/:id
  then go /posts/:id
}

page /posts/:id/delete {
  requires login
  button "Delete post" DELETE /api/posts/:id
  then go /posts/new
}
```

**Rules:**
- **Paths:** page paths follow the endpoint path rules (§5.1). A page and an endpoint can never share a path (RZ0334), so the convention is to put endpoints under `/api`. With an auth line, `/login`, `/signup`, `/account`, `/verify-email`, `/reset-password`, `/confirm-email` and `/privacy` are reserved for the built-in pages.
- **Parameters:** a page's `:parameters` fill in the parameters of the endpoint it shows, by name. Every page parameter must be used (RZ0323).
- **Never more open than its data (RZ0335):**
  - A page that uses (shows, or has a form or button for) a `requires login` endpoint must also `requires login`.
  - A page that uses an endpoint with `requires role` must require one of those roles.
- **Forms and buttons:**
  - A page has at most one `form` or `button` (RZ0337), followed by `then go` (RZ0338).
  - A form uses a POST, PUT or PATCH endpoint, and its inputs come from that endpoint's body: labels from field names, and limits (`required`, length, range) checked in the browser and again by the server. Links to the auth model are never inputs, because the server sets them.
  - An edit form (PUT or PATCH) starts with the current values when a GET endpoint exists on the same path.
  - A button uses a DELETE endpoint.
  - `then go` must name a page in the file. Its parameters come from the current page, and after a form `:id` can also be the id of the saved record.
- **Errors:** if the server rejects a form, its message appears next to the field it names, or above the button.
- **What a page shows:**
  - A `list` endpoint is shown as cards, with a "Load more" button for the next page.
  - A `find` endpoint is shown as a list of fields.
  - Only public fields appear, labelled from their names (`publishedAt` → "Published at").
  - When another page shows one record of the same model (for example `page /posts/:id { show GET /api/posts/:id }`), each card links to it.

**Built-in pages.** In an app with an `auth` line and at least one page:
- `/login` and `/signup` are generated, with forms for `/auth/login` and `/auth/signup`. `/login` also has "Log in with a passkey", and links to reset the password or get a new confirmation link.
- `/privacy` (with a `privacy for` line) shows the privacy notice (§4.2), and every page's menu links to it.
- `/confirm-email` opens from the link that confirms a new login email.
- `/verify-email` and `/reset-password` open from the emailed links: they confirm the email, or ask for a new password. Opened without a link, they ask for an email address and send a new link.
- `/account` (login required) lists the user's passkeys, and adds and removes them. It starts with forms to edit the profile, change the login email (confirmed by a link sent to the new address) and change the password. It also lists the devices the user is logged in on, with "Log out" for each and "Log out everywhere", lets the user create and revoke API tokens, download their data, and delete their account.
- Every page shows a menu with a link home, plus "Log in" and "Sign up", or "Account" and "Log out".
- A page that needs a login sends logged-out visitors to `/login?next=<the page>`. After logging in they return there. `next` is followed only if it is a path on this site.

**Branding: the `site` line.** One top-level line names the app and sets its look:

```
site "Rizo Blog" color teal logo "logo.png"
```

- The name appears in every page's title ("Write a post · Rizo Blog") and as the home link in the menu (1–60 characters).
- `color` sets the accent color for links and buttons: `blue` (the default), `teal`, `green`, `purple`, `pink`, `red`, `orange` or `gray`, each tuned for light and dark mode.
- `logo` is a PNG, JPEG or WebP file in the same folder as the `.rz` file (or a folder inside it), at most 256 KB. The build checks that its content really is such an image and serves it at `/_rizo/logo.png` (or `.jpg`, `.webp`). SVG is refused because SVG files can contain scripts.
- At most one `site` line (RZ0344). A logo that can't be read, isn't a real image or is too big stops the build (RZ0908).

**How pages are served:**
- The generated server answers `GET` for every page with a small HTML document.
- The browser runtime (`/_rizo/client.js`) builds the page from data in an inert JSON block, and fetches the data from the API with the same login cookie.
- If the page needs a login the visitor doesn't have, the server redirects to the login page, or answers 401 when the app has no login page. A missing role gets 403, and an invalid parameter gets 404.

**Safety:**
- Pages contain no HTML and no code.
- All text, both written in the file and coming from the database, is inserted as text and never interpreted as HTML. The runtime never uses `innerHTML`.
- Links, redirects after a form, and `?next=` can only point to this site.
- Pages are sent with a strict Content-Security-Policy that allows only the site's own script, stylesheet and images (the logo), and no inline scripts.

## 6. What the compiler generates

`rizolang build app.rz` writes everything to `dist/` in the current folder (and migrations to `migrations/` there). `rizolang check app.rz` only checks the file, including its logo, and writes nothing.

| File                 | Contents                                                                     |
|----------------------|------------------------------------------------------------------------------|
| `schema.sql`         | PostgreSQL 13+ tables, constraints, foreign keys and the sessions table, inside one transaction |
| `types.ts`           | `Model`, `ModelPublic` and `ModelInput` types for every model                |
| `routes.ts`          | Every endpoint as data, with its SQL written out in full                      |
| `runtime/pages.ts`, `runtime/client/` | Serves pages, plus the browser runtime and default styles (§5.6) |
| `migrate.ts`, `migrations/` | Applies the migrations from your project's `migrations/` folder (§6, Migrations) |
| `server.ts`          | The entry point                                                              |
| `Dockerfile`, `.dockerignore` | A container image for the app (see "Deploying") |
| `openapi.json`       | OpenAPI 3.1 description of every endpoint, also served at `/_rizo/openapi.json` (see below) |
| `reencrypt.ts`       | Only with `encrypted` fields: moves stored values to the current key (§3.2) |
| `runtime/`           | The Rizo runtime: validation, sessions, password hashing and the HTTP server |
| `package.json`, `tsconfig.json` | To install `pg` and type-check the app                            |

Everything except `schema.sql` and `types.ts` (`routes.ts`, `server.ts`, `migrate.ts` and `migrations/`, `openapi.json`, `Dockerfile` and `.dockerignore`, `runtime/`, `package.json` and `tsconfig.json`) is written only when the file has an `auth` line, `api` blocks or `page` blocks.

The three types:
- `User` is the stored record. It is for server use only, and holds a `PasswordHash`.
- `UserPublic` (`User.public`) leaves out Password and `private` fields.
- `UserInput` (`User.input`) is what a client sends. Passwords are plain text here, and links to the auth model are left out.

### openapi.json

Every build of an app with a server writes `openapi.json`, generated from the same route data the server uses, and the server also serves it at `GET /_rizo/openapi.json`. Agents and tools can read it to call the API correctly the first time.
- **Each endpoint:** its path parameters (`{id}`), `limit`, `after` and the `?name` filters for lists, the exact request body (with limits; unknown fields are refused), the response (`<Model>Public`: public fields only), and every error status with the `Error` shape.
- **Security:** endpoints that need a login accept the `session` cookie or a `token` (bearer API token).
- **Extensions:** `x-rizo-access` (`public` or `login`), `x-rizo-roles`, `x-rizo-owner` (`{ "field": "author", "orRoles": [...] }`) and `x-rizo-rate-limit` (`{ "requests", "perSeconds" }`).
- Account endpoints under `/auth` are described in §4, not in `openapi.json`.

### Migrations

Every build compares your models with the last build and records the difference in `migrations/`, next to your `.rz` file. Commit this folder to version control.

| File | Contents |
|------|----------|
| `migrations/0001_initial.sql` | The first schema |
| `migrations/0002_add_column_posts_views.sql`, … | One file per build that changed the schema |
| `migrations/rizo-schema.json` | A snapshot of the schema after the last migration. Don't edit it |

**Refused changes.** These changes would delete data, so the build stops (RZ0904) and writes no files, unless you run `rizolang build app.rz --allow-data-loss`:
- removing a model or field,
- changing a field's type, or adding or removing `encrypted`,
- removing a role.

Renaming looks like removing and adding, so it is refused too. Keep the old name.

**Other changes** are generated automatically: adding models, fields and links, and changing limits, `unique`, `optional`, roles and list indexes.
- Creating an index on a very large table can take a while, and blocks writes to that table until it's done. Apply such migrations at a quiet time.
- Making a field required, adding a required field, or tightening limits can fail if existing rows don't fit.
- In that case the migration is rolled back and nothing changes.

**Applying migrations.** `node migrate.ts` (in `dist/`) applies pending migrations in order.
- Each migration runs in one transaction and is recorded in the `_rizo_migrations` table.
- A lock stops two deploys from migrating at the same time.
- If an applied migration file was edited or deleted, nothing runs.

**Existing databases.** If a database was created from `schema.sql` before you used migrations, run `node migrate.ts --baseline` once. It records `0001_initial.sql` as already applied.

### Running the server

Needs Node.js 22.18 or newer.

**For development**, one command does everything:

```sh
DATABASE_URL=postgres://localhost:5432/app rizolang dev app.rz
```

`rizolang dev` builds, installs `pg` in `dist/` the first time, applies migrations and starts the server on port 3000 (`--port` to change it). It fills in development settings that aren't already set, and says which: `RIZO_PUBLIC_URL=http://localhost:3000`, printed emails (`RIZO_EMAIL_DEV=1`), a placeholder `RIZO_PRIVACY_CONTACT`, and a local encryption key kept in `dist/.dev-encryption-key`. Saving the `.rz` file rebuilds, migrates and restarts the server; if the file has errors, they are printed and the running server keeps going. Changes that would delete data still need `--allow-data-loss`, because migrations are committed and later run in production. Ctrl+C stops everything. It needs `DATABASE_URL` (RZ0906) and a file with an `auth` line, `api` or `page` blocks (RZ0907).

**In production**, run the steps yourself:

```sh
cd dist && npm install
DATABASE_URL=postgres://user:pass@localhost:5432/app node migrate.ts
DATABASE_URL=postgres://user:pass@localhost:5432/app node server.ts
```

To start a brand-new database, `psql "$DATABASE_URL" -f schema.sql` works too. Then run `node migrate.ts --baseline` so later migrations apply on top of it.

| Variable                    | Default     | Meaning                                                    |
|-----------------------------|-------------|------------------------------------------------------------|
| `DATABASE_URL`              | (required)  | PostgreSQL connection string                               |
| `PORT`, `HOST`              | `3000`, `127.0.0.1` | Where to listen                                    |
| `RIZO_ALLOWED_ORIGINS`      | none        | Comma-separated extra origins allowed to send POST, PUT, PATCH or DELETE requests |
| `RIZO_TRUST_PROXY`          | off         | `1` to read the client IP from `X-Forwarded-For` (only behind a trusted proxy) |
| `RIZO_DEV_INSECURE_COOKIES` | off         | `1` to drop the `Secure` cookie flag for local http. **Never in production.** |
| `RIZO_DB_POOL_SIZE`         | `10`        | Maximum number of database connections (1–1000)            |
| `RIZO_DB_STATEMENT_TIMEOUT_MS` | `5000`   | Longest time one query may run (100–600000). Slower queries are cancelled and answered with 503 |
| `RIZO_AUDIT_RETENTION_DAYS` | `365`       | How long security audit entries are kept (1–3650 days)     |
| `RIZO_ADMIN_EMAILS`         | none        | Comma-separated emails of **existing** accounts to make admins at startup (§4.1) |
| `RIZO_PUBLIC_URL`           | (required with `auth`) | The app's address for links in emails, e.g. `https://blog.example`. https, or http only for localhost. No path |
| `RIZO_EMAIL_API_KEY`        | (required with `auth`) | Resend API key |
| `RIZO_EMAIL_FROM`           | (required with `auth`) | Sender on a domain verified with Resend, e.g. `Blog <hello@blog.example>` |
| `RIZO_PRIVACY_CONTACT`      | (required with `privacy for`) | The email address people write to about their data, shown on the privacy page |
| `RIZO_ENCRYPTION_KEYS`      | (required with `encrypted` fields) | Comma-separated `id:key` pairs. The id is 1–16 lowercase letters or digits, the key 32 random bytes in base64 (`openssl rand -base64 32`). The first key encrypts; all of them decrypt |
| `RIZO_EMAIL_DEV`            | off         | `1` to print emails to the console instead of sending them (then the key and sender aren't needed). **Never in production** |

An app with an `auth` line refuses to start when the email settings are missing or invalid, and says which one to fix.

### Deploying

- **Docker:** `docker build -t my-app dist` builds an image from the generated `Dockerfile`: Node.js 24 on Alpine, only `pg` installed, running as the non-root `node` user, listening on `0.0.0.0:3000`. Apply migrations with `docker run --rm -e DATABASE_URL=... my-app node migrate.ts`, then run it with the settings above. `.dockerignore` keeps `node_modules` and local secrets out.
- **Health check:** `GET /_rizo/health` answers `{"status":"ok"}` when the database answers within 2 seconds, and 503 `{"status":"unavailable"}` otherwise or while shutting down. It says nothing else about the app. The Dockerfile's `HEALTHCHECK` uses it; point your platform's health check at it too.
- **Graceful shutdown:** on SIGTERM or SIGINT (for example `docker stop`), the server stops taking connections, lets requests in progress finish for up to 10 seconds, closes the database pool and exits.
- Behind a proxy or load balancer, set `RIZO_TRUST_PROXY=1` so rate limits and logs see the real client address.

### HTTP behaviour

- **Requests:**
  - Only `list` endpoints accept query parameters: `limit`, `after` (§5.4) and their own `?name` filters (§5.3). Any other query parameter gets 400.
  - Bodies must be JSON (`Content-Type: application/json`) and at most 1 MB. Endpoints without `body` reject a request body.
  - Path parameters are validated by type. An invalid id gets 400 before any query runs.
- **Responses** are JSON:
  - Errors look like `{ "error": { "code": "...", "message": "...", "field": "..." } }`.
  - Status codes: 400 invalid input, 401 not logged in, 403 cross-site request or missing role, 429 too many requests or attempts (`Retry-After`), 503 server busy or query too slow (`Retry-After`), 404 not found, 405 wrong method, 409 duplicate or still in use, 413 too large, 415 not JSON, 500 internal error (with a request id).
  - Every JSON response carries `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, `Cross-Origin-Resource-Policy: same-origin` and a `Content-Security-Policy` that allows nothing (`openapi.json` uses `Cache-Control: no-cache`).
  - Pages carry the page Content-Security-Policy (§5.6), the same `nosniff`, `X-Frame-Options`, `Referrer-Policy` and `no-store`, and `Cross-Origin-Opener-Policy: same-origin`. The runtime's files under `/_rizo/` are served with `nosniff`, `Cross-Origin-Resource-Policy: same-origin` and `Cache-Control: public, max-age=3600`.
- **Cross-site requests:** POST, PUT, PATCH and DELETE requests are rejected with 403 when the browser marks them as coming from another site (`Sec-Fetch-Site` is not `same-origin` or `none`), or when their `Origin` is another site. `RIZO_ALLOWED_ORIGINS` lists exceptions.
- **Password hashing** runs at most two at a time. If too many are waiting (a login flood), new requests get 503 with `Retry-After`, instead of slowing down every other request.
- **Logs:** one line per request: the method, the route pattern (such as `/posts/:id`), the status, the time and a request id. Logs never contain URLs with values, bodies, cookies or passwords.

## 7. Security guarantees

These are enforced by the compiler and the runtime, and each is covered by `tests/security.test.ts` (and, against a real database, `tests/e2e.test.ts`):

1. A Password or `private` field never appears in a `.public` type or in any response.
2. A Password is never stored in plain text.
3. All SQL is written at compile time. Request data only fills `$1, $2, …` parameters, and names can't break out of their quotes.
4. Every endpoint declares its access, and `requires owner` is enforced inside the query. Records that belong to a user can only be changed or deleted by that user.
5. A record's owner is always the logged-in user, and a user's role is only ever set by an admin. Neither is taken from the request body.
6. All input is validated against the model before it reaches the database, and unknown fields are rejected.
7. `GET` endpoints never change data. Cross-site writes are rejected.
8. Every endpoint, account endpoint and page is rate-limited, with counters shared by all server processes. Login, signup and password checks have their own stricter limits. No database query runs longer than the statement timeout (5 seconds by default). Security events are recorded in an audit log that never contains secrets.
9. When there is any compile error, or a change would delete data without `--allow-data-loss`, no output is written.
10. Pages contain no HTML or code. All text is inserted as text, links stay on the site, and pages are served with a strict Content-Security-Policy. A page is never more open than the data it shows.
11. A passkey works only on the site that created it, only once per challenge, and only with the user verified. The server never stores a private key, and a copied passkey (counter going backwards) is refused.
12. Signup, resending a confirmation link and asking for a password reset answer the same whether or not the email has an account. Emailed links work once, expire, are stored only as hashes and never appear in logs, and accounts can't log in before confirming their email.
13. Encrypted fields are stored only as AES-256-GCM ciphertext, tied to their column, and are decrypted only by the server. They can never be compared, sorted or made unique in the database.
14. An API token works only on the endpoints chosen for it, never on account endpoints, and never after it expires (at most 90 days) or is revoked. Only its hash is stored.
15. People can download everything stored about them, and deleting an account leaves no personal data behind: its records either go with it or are credited to a placeholder "Deleted user" account that can't be logged into.

## 8. Errors

```
app.rz:3:9 error RZ0301: Unknown field type "String" on field "User.name".
  3 |   name: String
    |         ^^^^^^
  fix: Use "Text" instead. Valid types: Text, Number, Bool, Email, Password, Date, ID, or a model name (User).
```

- The first line is always `<file>:<line>:<column> error <code>: <message>`. The `fix:` line says exactly what to change.
- Syntax errors (RZ01xx, RZ02xx) stop at the first error. Checking errors (RZ03xx) are all reported together.
- `rizolang` exits with 0 on success and 1 on any error.
- **`rizolang check app.rz`** reports the same errors without writing anything, and exits with 0 when the file is valid. With `--json` it prints `{ "rizolang", "ok": true, "file", "models", "endpoints", "pages", "auth" }`, or the errors as below.
- **`--json`** (`rizolang build app.rz --json`) prints one line of JSON to stdout instead, and nothing to stderr, for editors and AI agents. The exit codes are the same.

### Auditing: `rizolang audit`

`rizolang audit app.rz` reviews a file that builds and reports choices that are allowed but often a mistake. It writes nothing. Findings use the error format, with `warning` or `note` instead of `error`, and `--json` prints them as JSON (`findings`, each with `level`, and a `summary`). It exits with 1 when there are warnings (notes don't count), so it can run in CI.

| Code | Level   | Finding |
|------|---------|---------|
| RA01 | warning | A `public` endpoint that creates, changes or deletes data |
| RA02 | warning | A field whose name looks like personal data (phone, address, birth date, ID or card number, salary, health…) or a secret (token, API key, PIN) that isn't `private` |
| RA03 | note    | Such a field that is `private` but not `encrypted` |
| RA04 | warning | An `Email` field that isn't `private`, on a model that public endpoints return |
| RA05 | warning | A public `list` of the auth model |
| RA06 | warning | A `requires login` update or delete with no owner or role check |
| RA07 | note    | A public endpoint allowing more than 300 requests a minute |
| RA08 | note    | With `privacy for`: a model whose records belong to accounts but have no `keep` |

## 9. Common mistakes

The examples below use the `User` and `Post` models from §3.

**Types from other languages.**

```rizo
// Wrong
name: String
age: Int
active: Boolean
createdAt: DateTime

// Right
name: Text
age: Number
active: Bool
createdAt: Date
```

**Commas, semicolons, decorators or arguments in fields.**

```rizo
// Wrong
email: Email, name: Text;
name: Text(100)
email: Email @unique
nickname?: Text

// Right
name: Text max 100
email: Email unique
nickname: Text optional
```

**Declaring `id`, or snake_case names.**

```rizo
// Wrong
model blog_post {
  id: ID
  first_name: Text
}

// Right
model BlogPost {
  firstName: Text
}
```

**Weak or plain-text passwords.**

```rizo
// Wrong
password: Text
password: Password unique min 4

// Right
password: Password min 12
```

**Forgetting to say who may call an endpoint.**

```rizo
// Wrong
api GET /posts -> list Post.public {
  return db.Post.list()
}

// Right
api GET /posts -> list Post.public {
  public
  return db.Post.list()
}
```

**Letting the client choose the owner.**

```rizo
// Wrong
api POST /posts -> Post.public {
  requires login
  return db.Post.create(body)
}

// Right
api POST /posts -> Post.public {
  requires login
  return db.Post.create(body, author = me)
}
```

**Changing data without an ownership check, or with the wrong method.**

```rizo
// Wrong
api GET /posts/:id/delete {
  requires login
  return db.Post.delete(id)
}

// Right
api DELETE /posts/:id {
  requires login
  requires owner author
  return db.Post.delete(id)
}
```

**Returning the full record instead of the public view.**

```rizo
// Wrong
api GET /users/:id -> User {
  public
  return db.User.find(id)
}

// Right
api GET /users/:id -> User.public {
  public
  return db.User.find(id)
}
```

---

**A page with the same path as its endpoint, or with no access line.**

```rizo
// Wrong
page /api/posts {
  show GET /api/posts
}

// Right
page /posts {
  public
  show GET /api/posts
}
```

## 10. Grammar

```ebnf
file       = { model | auth | api | page | privacy | site } ;
site       = "site" TEXT [ "color" NAME ] [ "logo" TEXT ] NEWLINE ;   (color and logo in either order)
model      = "model" NAME "{" { field | keep } "}" ;
keep       = "keep" INT ( "day" | "days" | "month" | "months" | "year" | "years" ) NEWLINE ;
privacy    = "privacy" "for" REGION { "," REGION } NEWLINE ;
REGION     = "EU" | "UK" | "IN" | "US-CA" | "BR" ;
field      = NAME ":" TYPE { modifier } NEWLINE ;
modifier   = "unique" | "optional" | "private" | "encrypted" | "min" INT | "max" INT ;
TYPE       = "Text" | "Number" | "Bool" | "Email" | "Password" | "Date" | "ID" | NAME ;
auth       = "auth" NAME "by" NAME [ "roles" NAME { "," NAME } ] NEWLINE ;
api        = "api" METHOD PATH [ "->" rettype ] "{" { statement NEWLINE } "}" ;
METHOD     = "GET" | "POST" | "PUT" | "PATCH" | "DELETE" ;
PATH       = "/" [ segment { "/" segment } ] ;
segment    = word { "-" word } | ":" NAME ;
word       = ( LOWER | DIGIT ) { LOWER | DIGIT } ;
rettype    = [ "list" ] NAME "." "public" [ "with" NAME { "," NAME } ] ;
statement  = "public" | "requires" "login" | "requires" "role" NAME { "," NAME }
           | "limit" INT "per" ( "second" | "minute" | "hour" | "day" )
           | "requires" "owner" NAME [ "or" "role" NAME { "," NAME } ] | "return" query ;
query      = "db" "." NAME "." ACTION "(" [ arg { "," arg } ] ")" ;
ACTION     = "find" | "list" | "create" | "update" | "delete" ;
arg        = NAME | NAME OP value | "order" NAME [ "asc" | "desc" ] | "limit" INT ;
OP         = "=" | "!=" | "<" | "<=" | ">" | ">=" | "contains" ;
value      = NAME | "?" NAME | INT | "true" | "false" ;
NAME       = LETTER { LETTER | DIGIT } ;
INT        = [ "-" ] DIGIT { DIGIT } ;
page       = "page" PATH "{" { pageline NEWLINE } "}" ;
pageline   = "public" | "requires" "login" | "requires" "role" NAME { "," NAME }
           | "title" TEXT | "text" TEXT | "link" TEXT PATH | "show" METHOD PATH
           | "form" METHOD PATH | "button" TEXT METHOD PATH | "then" "go" PATH ;
TEXT       = '"' { any character except '"', '\\', newline, control; or '\\"' or '\\\\' } '"' ;
comment    = "//" { any character except newline } ;
```
